# 面试讲解指南

## 一分钟版本

平台解决“每换一个业务数据就重写 SQL 和看板”的问题。数据源先通过统一适配器读取 Schema，再用 YAML 把物理字段映射为用户、申请、时间、金额、渠道等业务角色。指标中心基于白名单生成安全 SQL，字段角色同时决定漏斗、留存、RFM、地区或机构分析是否可用。4,295,584 条 GA4 官方样例事件与 55,183 条 HMDA 真实申请已通过同一注册、查询、质量和图表框架实际接入，但业务口径保持独立。

## 关键追问

1. **如何证明不是写死三个 if/else？** 适配器只按存储类型分派；能力由映射集合计算；指标查询只读取配置。新增同结构数据只增加 YAML 与 Parquet，不改业务路由。
2. **如何防 SQL 注入？** 指标 ID 命中配置、维度白名单、标识符正则校验、过滤值参数绑定，前端无任意 SQL 参数。
3. **通用语义是否会抹平业务差异？** 不会。amount 只是角色，GMV、收入和发放金额的公式、名称、过滤和负责人都在各自指标配置中。
4. **为什么 HMDA 没有漏斗？** 公开数据一行是一个申请结果，没有同一申请的多阶段事件时间序列；平台主动禁用并解释，不伪造。
5. **如何做指标版本？** YAML 随 Git 版本化，指标带 owner/version；变更走测试和 PR，返回结果包含版本与生成 SQL。
6. **为什么用 DuckDB？** 它能高效直接查询 CSV/Parquet，便于三个独立仓库通过文件契约解耦；企业环境可把执行层换成 PostgreSQL/BigQuery 而保留语义层。
7. **旧项目为什么不保留 AI 作为核心？** 招聘目标更看重 SQL、数仓、指标和质量；AI 报告只适合作为可选消费层，不能替代可信数据底座。
8. **如何处理领域质量差异？** 通用层执行可配置的基础规则，领域仓库做深度对账；GA4 的 23 条缺失订单号在两层都保留为 warning，不被误报为平台故障或强行补值。
